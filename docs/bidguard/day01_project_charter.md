# BidGuard 项目章程 v0.1

> 日期：2026-06-29  
> 阶段：Week 1 / Day 1  
> 项目方向：IT、软件和网络服务类政府采购  
> 本文状态：已完成第一天内部评审，后续通过真实样本持续修订

## 1. 一句话定义

BidGuard 将真实公开招标文件转换为可追溯的要求与评分清单，生成投标响应矩阵，并结合确定性规则、检索和 LLM 对投标响应进行逐项完整性与一致性审查；所有高风险结论必须附原文证据并由人确认。

## 2. 为什么值得解决

招标文件通常同时包含资格要求、技术参数、商务条款、评分办法、合同草案、附件格式和更正公告。重要要求可能散落在正文、表格和附件中。团队依赖多人手工阅读和 Excel 核对，容易出现：

- 漏掉资格条件、实质性要求或废标风险。
- 技术要求没有分配负责人，截止前才发现未响应。
- 响应内容有承诺但没有证明材料或原文证据。
- 报价、工期、质保期等数据在不同文件中不一致。
- 更正公告发布后，旧版本要求仍被继续使用。
- 复核人员只看到模型结论，无法快速回到原文确认。

项目价值不是替人“写一份看起来很专业的标书”，而是减少漏项、缩短核对时间，并让审查过程可验证、可追责。

## 3. 首期用户

### 3.1 投标经理

- 目标：提交前知道哪些材料缺失、哪些条款存在高风险。
- 当前痛点：依赖经验和人工 Checklist，多个文件间难以保持一致。
- 成功体验：能按风险等级查看待处理项，并逐项确认或驳回。

### 3.2 售前/解决方案工程师

- 目标：快速拆解技术和服务要求，找到投标响应中的对应证据。
- 当前痛点：长文档阅读慢，技术参数和评分点散落，协作分工不清楚。
- 成功体验：系统生成响应矩阵，可分配负责人并定位招标原文。

### 3.3 商务或内部复核人员

- 目标：检查价格、日期、工期、质保和服务承诺是否一致。
- 当前痛点：同一信息重复出现在多个章节和表格中，人工比对容易遗漏。
- 成功体验：系统列出冲突值、出现位置和比较依据，由复核人作最终决定。

## 4. 三个核心业务场景

### 场景 A：招标要求拆解

输入一组招标公告、招标文件、技术附件和更正公告。系统输出：

1. 资格条件与所需材料。
2. 实质性要求和潜在废标项。
3. 技术参数、商务条款、交付与验收要求。
4. 评分项、分值、评分条件和证明材料。
5. 每条要求的原文、文件、页码、章节或表格坐标。

验收重点：关键条款不能因为章节、跨页表格或附件而漏掉。

### 场景 B：投标响应矩阵与审查

将投标响应文件与已确认的要求清单匹配。系统输出：

1. 要求—响应—证据—状态—负责人矩阵。
2. 未响应、部分响应、无证据承诺和数值不符。
3. 技术方案、商务条款和报价文件之间的矛盾。
4. 风险等级、置信度、规则/模型来源和原文证据。

验收重点：系统只报告有证据的风险；证据不足时标为“需人工确认”。

### 场景 C：更正公告影响分析

输入原招标文件和一个或多个更正公告。系统输出新增、删除和修改要求，重点提示技术参数、分值、资格、截止时间及合同条款变化，并同步更新响应矩阵。

验收重点：每个变化都能同时定位新旧原文，避免仅靠生成摘要。

## 5. 系统边界

### 5.1 输入

- 公开招标公告、招标文件、技术附件和更正公告。
- PDF、扫描 PDF、DOCX、XLSX 和 ZIP 附件。
- 用于开发与评测的受控投标响应样本。
- 用户对条款抽取、风险和证据的人工修订。

### 5.2 输出

- 结构化条款、评分项和要求来源。
- 可编辑、可导出的投标响应矩阵。
- 带证据、置信度和处理状态的风险清单。
- 新旧文件差异报告。
- 全流程审计记录和 Benchmark 指标。

### 5.3 人工决策边界

- 高风险条款、废标相关风险和低置信度抽取必须人工确认。
- 系统不能自动删除要求、修改用户文件或作最终废标判断。
- LLM 结论与确定性规则冲突时，两者都保留并进入人工复核。
- 人工修改必须记录修改人、时间、前后值和理由。

## 6. 明确非目标

1. 不自动提交投标，不接入电子招投标系统执行外部操作。
2. 不生成、伪造或补全企业资质、业绩、签章和证明材料。
3. 不预测中标概率，不输出法律意见或替代最终投标决策。
4. 不声称拥有非公开的真实完整投标文件。
5. v1.0 不覆盖全部行业，不做工程量清单计价和医疗参数专业判断。
6. v1.0 不追求全自动；可靠的人审闭环比“无人值守 Agent”更重要。

## 7. 数据真实性与合规边界

### 7.1 数据分层

- A 层：政府采购网站公开的招标公告、招标文件、附件和更正公告，按真实公开数据登记。
- B 层：公开中标公告、报价表和声明附件，按真实公开结果数据登记。
- C 层：依据真实要求构造的投标响应与缺陷样本，必须标记 `synthetic`，不得描述为真实供应商投标文件。

### 7.2 每个文件必须登记

- 来源页面和文件下载 URL。
- 发布机构、项目编号、公告日期和采集日期。
- SHA-256、文件类型、大小和文档角色。
- 是否公开可访问、是否允许在公开仓库再分发、判断依据。
- 脱敏状态、解析状态和解析器版本。

公开可访问不自动等于允许重新分发。权利状态不清晰时，GitHub 只发布 Manifest、下载方式、标注和必要的少量引用，不打包上传原文件。

## 8. v1.0 成功标准

### 8.1 业务成功标准

- 复核人员能在一个界面完成“要求—响应—证据—状态”检查。
- 对 Benchmark 中的关键资格/废标/技术条款，抽取 Recall 目标不低于 95%。
- 对受控审查案例，风险 Recall 目标不低于 90%，Precision 目标不低于 80%。
- 所有高风险结论均提供可打开的原文位置；引用正确率目标不低于 95%。
- 更正公告中的关键数值和日期变化能被检测并回溯新旧原文。

### 8.2 工程成功标准

- 50 个真实公开项目的数据清单，200 条 Gold Clause、100 条检索问题和 40 个审查案例可复现。
- 提供 Naive RAG、混合检索、重排、规则+LLM 等对照和消融实验。
- 长任务支持状态查询、取消、失败重试、Checkpoint 和人工中断恢复。
- 项目级权限隔离；安全测试中跨项目越权和恶意压缩包成功次数为 0。
- 新环境能在 30 分钟内启动，测试、评测、Docker 和 CI 文档完整。

以上均为目标值。最终 README 和简历只允许填写实际测得的数据。

## 9. 主要风险与应对

| 风险 | 影响 | 当前应对 |
| ---- | ---- | -------- |
| 完整真实投标文件不公开 | 无法直接建立真实端到端审查集 | 用真实招标要求构造受控响应，并明确标记、人工复核 |
| PDF 表格和扫描件解析不稳定 | 关键条款丢失，后续流程失真 | 建版面解析 Baseline、OCR 回退、页级置信度和人工校正 |
| 资格/废标判断具有专业风险 | 错误结论可能误导用户 | 高 Recall 预警、证据展示、免责声明和强制 HITL |
| 公开访问与再分发权不同 | 公开仓库可能产生合规问题 | 保存来源/哈希，默认发布 Manifest 和下载脚本 |
| 项目范围过大 | 20 周无法形成可评测闭环 | 首期限制 IT/软件/网络服务，先做三个核心场景 |
| LLM 输出不稳定 | 指标不可复现 | 固定模型/Prompt 版本、结构化输出、规则优先和回归集 |
